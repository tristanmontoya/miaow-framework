Runtime orchestration¶

class TaskExecutor¶

Base class for model-specific task executors.

The only requirement of a TaskExecutor is that it must implement an execute method that takes a Task and returns a caf::result<TaskResult>, which can be an immediate result, a CAF error, or a delegated response. Operation failures use a failed TaskResult; CAF errors describe request or protocol failures. The class is intended to be subclassed by concrete implementations that define the specific behavior of the task executor.

Subclassed by miaow::DynamicBmiTaskExecutor, miaow::StaticBmiTaskExecutor< BmiModelType >

class JobController¶

Per-job policy for configuring units and responding to execution results.

One controller belongs to each job and stays in the parent process. The job actor serializes its hooks, so controller members accessed only by these hooks need no mutex. Hooks should return promptly: blocking work delays results, shutdown, and job timeouts.

Controllers add work through Job::add_task(), in task-ID order. The runtime prepares and dispatches that work after the hook returns. With batch-synchronous policy, tasks added during initialization form the first batch alongside caller-provided tasks; tasks added by each callback form the next batch. Failed tasks count toward completion.

Called once before dispatch, including when the caller supplied initial tasks.

virtual void callback(Job &job, std::span<const TaskRecord> completed_tasks, std::span<const UnitFailure> failed_units)¶

Respond to completed tasks and unavailable simulation units.

Spans are borrowed for this call and must not be retained. Asynchronous callbacks receive an operation completion or the tasks affected by unit loss. Batch callbacks receive all completions and unit failures from the current batch. The default policy fails the job on unit loss and permits reported task failures. Unit loss also fails accepted tasks targeting that unit. Batch policy waits for the current batch before reporting unit failures. Units are never rebuilt implicitly. Synthetic job-timeout records remain only in the final JobRecord.

Parameters:

  • job – Job whose work and unit lifetimes the controller manages.

  • completed_tasks – New completions in completion order, delivered once per task.

  • failed_units – Units whose execution context is unavailable.

inline virtual caf::config_value finalize()¶

Return structured output for the final JobRecord.

Called once by the job actor on completion, including a job timeout or an empty job. Calls are serialized with callback(), and this method should return promptly. Implementations may move accumulated data into the result. Task-generation errors and runtime shutdown produce no final record and do not call this method. Exceptions propagate through JobHandle::get() as job errors.

Returns:

Optional scalar, list, or dictionary output; null by default.

int miaow::run_subprocess_worker(int argc, char *argv[], std::function<TaskResult(const Task&)> task_handler)¶

Run a subprocess worker that handles serialized tasks from its parent.

Every executable registered with TaskExecutorRegistry::add_subprocess() must call this function once from its main() and pass the supplied argc and argv unchanged. The handler runs serially for each received Task, and a persistent subprocess may invoke the same handler more than once. An exception from the handler produces a failed TaskResult.

Parameters:

  • argc – Command-line argument count supplied to the subprocess executable.

  • argv – Command-line arguments supplied to the subprocess executable.

  • task_handler – Callable that executes one received Task and returns its TaskResult.

Returns:

Zero after orderly worker shutdown or one after setup failure.

class Runtime¶

Actor runtime for orchestrating simulation Tasks.

The runtime is model-agnostic and thread-safe. Each job manages its simulation units. Each SimulationUnit owns its executor instance and any subprocess resources. The controller handles unavailable units; its default policy fails the job.
