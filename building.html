Building, testing, and installation¶

Prerequisites¶

MIAOW requires CMake 3.30 or newer, a C++20 compiler, and a Fortran compiler. The CAF, JSON, and Boost provider options specify where CMake obtains these dependencies: from packages already installed on the system, by fetching and building them from source, or by trying the system first and fetching them if necessary. Boost is needed only when building the job record checker. See Build options for a description of the available provider settings.

On Ubuntu, the required compiler and build tools can be installed with the following command:

sudo apt-get install build-essential cmake gfortran

On macOS with Homebrew, the required compiler and build tools can be installed using the following commands:

sudo xcode-select --install  # if Apple's Command Line Tools are not installed
brew install cmake gcc

Repository development build¶

The repository can be configured and built with the following commands:

cmake -S . -B build
cmake --build build

CITATION.cff is the single source for the software version. Use version: "0.3.0-dev" during development and version: "0.3.0" for a release; CMake extracts 0.3.0 and automatically reconfigures when the citation file changes.

With BUILD_TESTING=ON (the default), CMake builds a Boost.Test checker for each regression workload, the lifecycle and BMI dispatch test drivers, and the six examples required by the standard regression suite: 00_hello, 01_heat, 03_dynamic_bmi, 07_job_controller, 09_bmi_operations, and 10_model_coupling. Their tests are registered even with BUILD_EXAMPLES=OFF. See Build options for the components built in each configuration, and Building examples to select additional examples.

Run the tests enabled in the current build with the following command:

ctest --test-dir build --output-on-failure

A single test can be selected by name with the following command:

ctest --test-dir build -R <test_name> --output-on-failure

Building examples¶

BUILD_TESTING=ON always includes the six regression examples. BUILD_EXAMPLES=ON adds the examples selected by MIAOW_EXAMPLES; overlapping selections are built once. To build the selected examples without the regression suite:

cmake -S . -B build -DBUILD_TESTING=OFF -DBUILD_EXAMPLES=ON
cmake --build build

Override the selected example set with a semicolon-separated MIAOW_EXAMPLES value, for example -DMIAOW_EXAMPLES="00_hello;01_heat". This selection supplements the required regression examples when testing is enabled. A normal cmake --build build builds every included example; use --target miaow_hello to narrow the build to that specific target.

Each model-backed example accepts a MIAOW_<MODEL_NAME>_MODEL_ROOT override. When the override is empty, CMake resolves the source beneath MIAOW_DEFAULT_MODEL_BASE_DIR. If the resolved directory is missing and the example declares a Git repository and revision, CMake fetches the model into that directory. See Examples for model-specific dependencies and options.

Regression tests¶

CI runs the simulation-unit lifecycle cases and the regression tests for the default examples on every push and pull request. To run the same suite locally:

cmake -S . -B build -DBUILD_TESTING=ON -DBUILD_EXAMPLES=OFF
cmake --build build
ctest --test-dir build -L regression --output-on-failure

CTest runs Boost.Test checkers using the example and driver job builders. Numerical assertions inspect JobRecord; report assertions inspect job_record.json. JSON cases in tests/cases define inputs, expected failures, and runtime options.

Tests cover BMI execution, unit removal and replacement, and callback delivery. Lifecycle coverage includes both callback policies and execution with one or two workers.

Tests using dedicated drivers¶

BMI task dispatch driver¶

These cases use tests/bmi_task_dispatch.hpp. The five execution paths are a statically linked C++ model, C++ and Fortran plugins in-process, and C++ and Fortran plugins in subprocesses.

The initialization and finalization failure cases use a custom exception in the static test model. Its destructor records whether the model is still alive, and the checker requires exception destruction before model destruction. This checks the lifetime ordering needed to keep plugin exception code available.

miaow_subprocess_shutdown_within_grace

simulation_unit_lifecycle.hpp and subprocess_shutdown_worker.cpp

Times out a child task that subsequently returns and completes destructor cleanup within the shutdown grace period.

The child exits normally and writes its cleanup marker. The active and queued tasks fail once with one unit-failure report, the queued task never dispatches, new work on the failed unit is rejected, and the worker slot becomes available only after the child is reaped.

miaow_subprocess_shutdown_grace_expired

simulation_unit_lifecycle.hpp and subprocess_shutdown_worker.cpp

Times out a child task whose destructor cleanup exceeds the configured grace period.

The child starts cleanup but is terminated by SIGKILL before finishing it. The timeout remains the failure cause, the child is reaped, queued work never dispatches, and the independent unit can then use the worker slot.

Library installation build¶

The following example configures a build without tests and selects $HOME/.local as an example installation prefix. Any writable installation path can be supplied through CMAKE_INSTALL_PREFIX:

cmake -S . -B build \
    -DBUILD_TESTING=OFF \
    -DBUILD_EXAMPLES=OFF \
    -DCMAKE_INSTALL_PREFIX="$HOME/.local"

cmake --build build
cmake --install build

This configuration builds and installs the miaow C++ library, the iso_c_bmi Fortran BMI bridge, and the miaow_subprocess BMI worker executable.

Building MIAOW from source requires C++20 and Fortran compilers. The completed installation can be used by a C++-only project without enabling Fortran or requiring a Fortran compiler.

Using the installed package¶

In another project, define the executable or library that uses MIAOW and link it to the installed miaow::miaow target. For example, a minimal downstream CMakeLists.txt is:

cmake_minimum_required(VERSION 3.30)

project(my_program LANGUAGES CXX)

find_package(miaow CONFIG REQUIRED)

add_executable(my_program main.cpp)
target_link_libraries(my_program PRIVATE miaow::miaow)

The imported target supplies the installed MIAOW include directory, requests C++20, and links the required CAF, nlohmann/json, and procedural BMI bridge libraries. Source files can include miaow.hpp, miaow_bmi.hpp, and miaow_io.hpp as needed.

A custom subprocess worker is another executable linked against miaow::miaow:

add_executable(my_worker worker.cpp)
target_link_libraries(my_worker PRIVATE miaow::miaow)

When the selected installation prefix is outside CMake’s normal search locations, the downstream configuration supplies the same path through CMAKE_PREFIX_PATH:

cmake -S . -B build -DCMAKE_PREFIX_PATH="$HOME/.local"
cmake --build build

The MIAOW package locates the required CAF components and nlohmann/json when find_package(miaow) runs. Both packages must be discoverable through the system installation, CMAKE_PREFIX_PATH, or the downstream project’s CMake toolchain. Nlohmann/json supplies the return type of miaow::to_json() in miaow_io.hpp. The installed procedural BMI bridge depends on a compatible Fortran runtime library, such as libgfortran when the bridge is built with GNU Fortran. This runtime library must remain available when an application that links to MIAOW runs, but compiling the downstream project does not require a Fortran compiler.

Note

Configure CMAKE_INSTALL_PREFIX before building so bmi_subprocess_executable_path() can locate the installed worker. Changing only cmake --install build --prefix <path> does not update this lookup. If you relocate the installation, reconfigure and rebuild MIAOW or pass the installed worker path directly to TaskExecutorRegistry::add_subprocess().

Build options¶

All top-level repository configurations build the following runtime components, which are installed by cmake --install:

  • miaow: the static C++ library containing the runtime, job and unit APIs, and BMI task executors.

  • iso_c_bmi: the shared Fortran BMI bridge. It exposes C-compatible functions so MIAOW’s C++ code can call Fortran BMI models, both in-process and in subprocesses.

  • miaow_subprocess: the built-in BMI worker executable. MIAOW starts it when a subprocess-backed unit first needs it and reuses it for that unit’s tasks.

The standard regression suite is enabled when BUILD_TESTING is ON, and builds the following additional programs:

  • <target>_checks: Boost.Test executables sharing the corresponding example or driver workload and its model linkage. They check numerical results in process and inspect the final report schema and controller observations.

  • miaow_simulation_unit_lifecycle_driver: the model-free workload driver for removal, failure recovery, callback delivery, and task dependencies.

  • miaow_bmi_dispatch_driver: the heat-model workload driver for operation failures, value transfers, and repeated runs across the five BMI execution paths.

  • The 00_hello, 01_heat, 03_dynamic_bmi, 07_job_controller, 09_bmi_operations, and 10_model_coupling example programs, including the heat-model libraries and C++ and Fortran plugins needed by their tests.

  • auto: try find_package(...), then use FetchContent if not found

Documentation build¶

The generated API documentation uses Doxygen for C++ documentation-comment extraction and Sphinx with Breathe for HTML rendering. Architecture diagrams use Mermaid sources in docs/diagrams, rendered by sphinxcontrib-mermaid. Doxygen must be installed separately and available on PATH.

The following commands create a dedicated Python environment and build the documentation:

python3 -m venv docs/.venv
docs/.venv/bin/pip install -r docs/requirements.txt
docs/.venv/bin/sphinx-build -E -n -b html -d docs/_build/doctrees docs docs/_build/html

The generated HTML entry point is docs/_build/html/index.html.
