Examples¶

Run examples from their own examples/<example_name> directories:

cd examples/00_hello
./miaow_hello
cd ../01_heat
./miaow_heat
cd ../02_soil_freeze_thaw
./miaow_soil_freeze_thaw --output_root ./output --max_workers 2
cd ../03_dynamic_bmi
./miaow_dynamic_bmi --output_root ./output --max_workers 2
cd ../04_summa
./miaow_summa --realization data/realization_config.json --output_root ./output

Included examples¶

  • examples/00_hello: minimal orchestration and diagnostics output

  • examples/01_heat: BMI integration using the CSDMS heat example

  • examples/02_soil_freeze_thaw: many-task SoilFreezeThaw workflow with per-task forcing, including matched, short, and long forcing cases

  • examples/03_dynamic_bmi: dynamic C++ and Fortran BMI plugin integration using the CSDMS heat examples

  • examples/04_summa: SUMMA run using subprocess pipeline execution and one MIAOW task per staged catchment feature described by a NextGen-style realization

The SUMMA example runs in a subprocess and is built through its upstream summabmi target. The example CMake file fetches the develop branch into third_party/summa and builds directly from SUMMA’s build/CMakeLists.txt.

SUMMA test data¶

The SUMMA example provides a small test configuration with five catchments from the Oyster River gauge_01073000 case. The configuration consists of these files: data/configs/cat-*.input, data/forcings/*_forcing.csv, data/settings/SUMMA/*, data/catchments.geojson, and data/realization_config.json.

After fetching SUMMA and creating the preprocessing environment, regenerate the forcing CSVs manually with this command:

./scripts/preprocessing/.venv/bin/python \
  ./scripts/preprocessing/stage_summa_gauge_forcing_csvs.py

Example layout¶

Each example directory follows a common layout:

examples/<example_name>/
  data/             # example input data, tracked in the repository
    configs/        # configuration files
    forcings/       # forcing data files, when needed
    settings/       # model settings and parameter files, when needed
  extern/           # symlinks to model sources, created by CMake
  output/           # runtime and model output, generated and not tracked

Configuring model examples independently¶

These flags are relevant when configuring from an example directory or another project:

Flag

Default

Description

-DMIAOW_ROOT

<example_dir>/../..

Path to the miaow-framework source tree

-DMIAOW_DEFAULT_MODEL_BASE_DIR

${MIAOW_ROOT}/third_party

Default base directory where external model sources are resolved or fetched

-DEXECUTABLE_TARGET

example default

Override executable target name

The helper cmake/miaow_bmi_model.cmake provides miaow_add_bmi_model(...) and miaow_add_workflow_test(...) for model integration and workflow tests. Model examples keep their MIAOW-specific source and input files under examples/<example_name>/.

External BMI model source is resolved separately: each model-backed example uses its corresponding MIAOW_*_MODEL_ROOT override when set, otherwise it resolves to ${MIAOW_DEFAULT_MODEL_BASE_DIR}/<model-subdir>. If a required source directory is missing and the example declares a Git repository and tag, CMake fetches the model from GitHub into the resolved location under MIAOW_DEFAULT_MODEL_BASE_DIR.

Example command-line options¶

Examples use the following runtime command-line options where applicable:

Option

Default

Description

--max_workers

1

Maximum number of worker actors used for each job

--task_request_timeout

5

Timeout for task requests sent to worker actors, in seconds

--job_request_timeout

300

Timeout for job result requests, in seconds

--output_root

""

Root directory path for runtime-managed output folders, disabled by default

--realization

data/realization_config.json

BMI realization path

Public CLI parsers throw std::runtime_error for unrecognized arguments, missing option values, and invalid option values. Example executables catch these errors, print the message, and exit with status 1.
