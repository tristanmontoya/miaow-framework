BMI integration¶

MIAOW runs models implementing the Basic Model Interface (BMI) either in the parent process or in a unit-owned subprocess. See Examples for complete programs and API reference for configuration fields and function signatures.

BMI task lifecycle¶

job.add_task(unit, "run", config) adds a complete-run task targeting the given unit. The configuration is a caf::config_value::dictionary, stored as one argument in Task::args_. Standalone tasks can be constructed with Task{unit, "run", config}. Each execution performs one complete model run:

  1. Construct or load a fresh BMI model and call Initialize(init_config).

  2. Call Update() until the model reaches its end time.

  3. Call Finalize() and release the model before reporting success.

Models manage their own forcing and scientific output. If a BMI call fails, the runner attempts to finalize a successfully initialized model before releasing it. Results report the number of completed updates.

A unit retains its executor across operations. Each run operation constructs a fresh model; model state does not persist between complete runs. Static and dynamic BMI executors, including the bundled subprocess worker, also support individual operations on a retained model, as described below.

Configuration dictionaries use these fields. Fields with defaults may be omitted; supplied values must have the expected type and satisfy the model’s requirements.

When init_config is omitted from the configuration dictionary, the model receives an empty initialization path. Models that require an initialization file must still be given its path. Dynamic initialize and run tasks require the addition of plugin_path to specify what plugin library to load.

Static BMI model¶

Register the concrete C++ model type, declare a unit, and add its run operation:

miaow::TaskExecutorRegistry registry;
const miaow::TaskExecutorId heat =
    registry.add<miaow::StaticBmiTaskExecutor<BmiHeat>>();
miaow::Runtime runtime(registry);
miaow::Job job;
const miaow::SimulationUnitHandle unit = job.add_unit("heat", heat);
caf::config_value::dictionary config;
config.insert("init_config", heat_config);
job.add_task(unit, "run", config);

// Submit the job
miaow::JobHandle job_handle = runtime.submit_job(std::move(job));

// Wait for completion and retrieve the job record
const miaow::JobRecord record = job_handle.get();

For concurrent independent runs, declare one unit per configuration using the same executor registration. Repeated tasks targeting one unit execute sequentially and reuse its executor.

Individual BMI operations¶

StaticBmiTaskExecutor and DynamicBmiTaskExecutor inherit their operation handling and model ownership from BmiTaskExecutor. Use job.add_task(unit, "initialize", config) with a configuration dictionary to initialize a retained model, followed by argument-free job.add_task(unit, "update"), get_current_time, and finalize tasks. The same dictionary can be used for initialization or a complete run when it includes the required fields. Direct static initialization with job.add_task(unit, "initialize", path) is also supported.

Express required operation order with explicit dependencies, or submit each operation from a controller callback after its predecessor succeeds. A later ready operation can overtake an earlier operation waiting on a dependency, even on the same unit:

const miaow::TaskHandle initialized = job.add_task(unit, "initialize", config);
const miaow::TaskHandle updated = job.add_task(unit, initialized, "update");
const miaow::TaskHandle queried =
    job.add_task(unit, updated, "get_current_time");
job.add_task(unit, queried, "finalize");

These dependencies require successful predecessors. If an operation fails, its dependent finalizer also fails without dispatch. A controller can submit a separate finalization task after receiving the failure record to attempt cleanup.

The bundled subprocess worker retains one DynamicBmiTaskExecutor in each unit’s child process and supports the same operations and task payloads.

The exposed individual operations are initialize, update, get_current_time, get_value, set_value, and finalize. Grid queries and indexed value access are not exposed as task operations. get_current_time returns a scalar double in TaskResult::output_, in the model’s native time units.

The executor retains the model until finalization and can initialize a fresh model afterward. Dynamic models retain their loaded plugin for that lifetime. Updates, time queries, value access, and finalization require an initialized model. run and a second initialize are rejected while a model is retained. Clock tolerance applies only to complete runs.

A failed initialization releases the model. Exceptions during updates, queries, or value access, including argument and metadata errors, leave the retained model usable only for finalization. A finalization attempt releases the model even if it fails. Submit finalize explicitly to receive its result; executor destruction attempts cleanup but cannot report errors as task results.

The 09_bmi_operations example initializes one heat model, queries its time, performs two updates with a query after each, and finalizes. The 01_heat example performs a complete run.

Complete-variable value access¶

job.add_task(unit, "get_value", variable_name) returns the complete variable as a flat caf::config_value::list in TaskResult::output_. job.add_task(unit, "set_value", variable_name, values) copies a flat list into the variable and returns success without output. Scalars use one-element lists. Values follow the model’s flattened ordering; no spatial mapping or unit conversion is performed.

BMI metadata selects a native float, double, or int buffer. Setters require CAF real elements for floating-point variables and CAF integer elements for integers. Reads represent floats exactly as doubles; writes to float variables apply normal rounding. Finite values outside the float range and integers outside the native int range are rejected. NaN and infinity are preserved.

Item sizes must match the native type, byte counts must be non-negative multiples of the item size, and setter lists must match the element count. Unsupported types or inconsistent metadata fail the task. The Fortran bridge translates real/float to float, integer/int to int, and double/float64/double precision to double.

Use dependencies and output_of() to transfer values between models, as shown in Architecture. Source and destination variable names may differ. The workflow must ensure compatible units and grid layouts; the executor checks the destination type and size.

Dynamic BMI plugin¶

Register DynamicBmiTaskExecutor for in-process plugin execution, or register the bundled executable for subprocess isolation. The configuration selects a C++ or Fortran plugin and its initialization file:

miaow::TaskExecutorRegistry registry;
const miaow::TaskExecutorId executor =
    registry.add_subprocess(miaow::bmi_subprocess_executable_path());
miaow::Runtime runtime(registry);
miaow::Job job;
const miaow::SimulationUnitHandle unit = job.add_unit("model", executor);
caf::config_value::dictionary config;
config.insert("backend", "fortran");
config.insert("plugin_path", plugin_path);
config.insert("init_config", init_config);
job.add_task(unit, "run", config);

// Submit the job
miaow::JobHandle job_handle = runtime.submit_job(std::move(job));

// Wait for completion and retrieve the job record
const miaow::JobRecord record = job_handle.get();

A subprocess-backed unit keeps its child and dynamic executor alive between operations until removal or job completion. Individual operations retain an initialized model and its plugin; complete run tasks each create and finalize a fresh model. The Julia/Trixi example places one simulation in a dedicated unit subprocess.

Schedule finalize before normal unit removal or job completion to receive the model’s cleanup result. On unit removal, job completion, task or job timeout, and Runtime destruction, subprocess shutdown requests orderly worker exit. After the active call returns, the bundled worker releases its executor, which attempts finalization if a model remains.

RuntimeOptions::subprocess_shutdown_grace_period_ allows 5 seconds by default for the active call, finalization, and process exit; expiry forcibly terminates the child. Finalization is best effort and cannot run after forced termination or a process crash. Unexpected child termination also loses the retained model; MIAOW reports a unit failure rather than recreating its state.

Custom executables can implement the same task contract.

Dynamic C++ plugins must export the bmi_model_create() and bmi_model_destroy(...) symbols as C linkage. Dynamic Fortran plugins must export register_bmi(void**) for the linked NOAA-OWP iso_c_fortran_bmi bridge. See examples/03_dynamic_bmi for examples of concrete C++ and Fortran plugin workflows.

Model timekeeping¶

time_step_tolerance_seconds defines the absolute tolerance for the final-time comparison. When omitted, it uses miaow::default_bmi_time_step_tolerance_seconds (1e-4 seconds). An explicit value overrides the default. It must be finite, non-negative, and less than half the model time step. MIAOW converts the tolerance to the units reported by GetTimeUnits(), supporting seconds, minutes, hours, and days with common abbreviations and singular or plural names.

The runner calls Update() repeatedly and fails the task if an update passes the end time beyond this tolerance. A model already at its end time receives initialization and finalization with no updates.

Diagnostics and artifacts¶

When RuntimeOptions::output_root_ or CLI --output_root is set, MIAOW writes a job_record.json under <output_root>/run_<run_id>/job_<job_submission_id>/. Records include unit and executor identifiers, operations, status, messages, metadata, structured output, timings, and artifact paths. Subprocess stdout and stderr logs may also be retained there.

Scientific output files and their locations are controlled by the model’s initialization configuration. BMI tasks produce no additional scientific output or resolved configuration files.
